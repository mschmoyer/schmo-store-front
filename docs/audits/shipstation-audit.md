# ShipStation Integration Audit

Scope: `src/lib/shipstation/**`, `src/app/api/shipstation/**`, `src/app/api/admin/sync/**`, `src/app/api/admin/integrations/shipstation/**`, `src/app/admin/integrations/**`, `scripts/background-sync.js`, `database/migrations/{005,007,008,012,014,015}*.sql`, `docs/shipstation-api-openapi.yaml`. Live schema verified against `PGPASSWORD=postgres psql -h 127.0.0.1 -U postgres -d rebelshops`.

---

## Verdict

"Robust workflow support powered by the ShipStation API" is not currently true. The codebase contains two parallel, half-finished ShipStation integrations — a legacy XML "Custom Store" polling API and a modern V2 REST API — that don't agree with each other, and neither is robust. The setup screen a new merchant is told to use (`/admin/integrations/shipstation`) displays credentials that the server will not actually accept, its "Test Connection" button never contacts ShipStation, and its "Generate Credentials" endpoint calls two Postgres functions that were dropped by a later migration and no longer exist — confirmed live against the database, this 500s every time. The scheduled background sync documented in `CLAUDE.md` as the product's automation story is dead end-to-end: it queries a table (`integrations`) that doesn't exist in the schema, and even if that were fixed, its internal HTTP calls use a bearer token the auth layer cannot verify. The `sync_logs` table, which exists specifically to record these runs, has zero rows in the live database. The one piece that does work — pushing a paid order into ShipStation as a V2 shipment — calls an endpoint (`POST /v2/shipments`) that has no documented `POST` operation anywhere in the OpenAPI contract this audit was asked to check against, runs synchronously in the checkout request path with no retry, and will hard-fail the sale if ShipStation hiccups. The webhook receiver that's supposed to bring tracking numbers back has no signature verification (the verification function exists and is simply never called), no tenant scoping (any caller can mark any store's order shipped), and is never actually subscribed with ShipStation by any code path, so in practice it is unreachable. Credential "encryption" is base64. This is a demo that resembles an integration, not one a merchant can depend on to run their store.

## P0 Findings

### P0-1: The ShipStation setup screen shows the merchant credentials the server will not accept
- **Evidence:** `src/app/admin/integrations/shipstation/page.tsx:156-182` (`generateCredentials()`) generates a username/password with client-side `Math.random()` (via `generateSecurePassword`/`generateSecureApiKey` in `src/lib/shipstation/utils.ts:222-267`) and tells the merchant (lines 660-681, "Setup Instructions") to copy these into ShipStation's Custom Store form. But `src/app/api/admin/integrations/shipstation/route.ts` POST handler (lines 186-239) never reads `username`/`password` from the request body at all — it computes an entirely different, deterministic username/password server-side from `store_id` + `apiKey` via `generate_shipstation_username_deterministic`/`generate_shipstation_password_deterministic` (lines 230-238), and that's what `authenticateShipStationRequest` (`src/lib/shipstation/auth.ts:71-141`) actually checks against on every ShipStation request. After save, the client only re-masks the `apiKey`/`apiSecret` fields (`shipstation/page.tsx:296-304`); it never re-populates `username`/`password` from the server's authoritative response, so the screen keeps showing the fake, unusable credentials.
- **Why it matters:** Any merchant who follows the on-screen instructions verbatim configures ShipStation with credentials that will 401 against `/api/shipstation/orders`. This is the single most important "day one" flow in the product and it is broken by construction, not by edge case.
- **Fix:** Delete the client-side random credential generator; render only the credentials the server actually issues (returned in the POST response, or re-fetched via GET which already computes them correctly at `route.ts:129-147`). Never display editable username/password fields that don't round-trip to what auth checks.
- **Effort:** S

### P0-2: The "Test Connection" button never talks to ShipStation
- **Evidence:** `src/app/api/admin/integrations/shipstation/test/route.ts` — every check (`testBasicAuth`, `testApiCredentials`, `testEndpointUrl`, `testShipStationCompatibility`, lines 102-330) is a local regex/length check. The code comments say it outright: "Simulate ShipStation's connection test... This would normally make a test request to ShipStation's API... For now, we'll simulate" (lines 260-262). A key of `"aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa"` and secret `"bbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbb"` passes with "ready for integration."
- **Contrast:** A real check exists elsewhere — `src/app/api/admin/integrations/test/route.ts:83-91` genuinely calls `GET https://api.shipstation.com/v2/warehouses` — but it's wired to the *other*, generic integration UI (`IntegrationSettings.tsx`), not to this screen.
- **Why it matters:** Answers audit question 1 directly: there is no real pre-flight validation on the path merchants are told to use. The first time an invalid/revoked key is actually exercised is a live customer checkout (`src/app/api/orders/route.ts:62-78`), where it now fails the sale instead of failing setup.
- **Fix:** Point this screen's test button at the real V2 credential check (`testShipStationV2Credentials`, `src/lib/shipstation/v2Api.ts:459-484`) or the working `/api/admin/integrations/test` handler.
- **Effort:** S

### P0-3: `generate-credentials` endpoint calls database functions that no longer exist
- **Evidence:** `src/app/api/admin/integrations/shipstation/generate-credentials/route.ts:46-53` calls `generate_shipstation_username($1)` and `generate_shipstation_password()`. Migration `008_deterministic_shipstation_auth.sql:8-10` explicitly drops both: `DROP FUNCTION IF EXISTS generate_shipstation_username(UUID); DROP FUNCTION IF EXISTS generate_shipstation_password();`. Confirmed live: `psql \df generate_shipstation*` on the project's own Postgres returns only `generate_shipstation_username_deterministic` and `generate_shipstation_password_deterministic` — the two non-deterministic functions this route calls do not exist.
- **Why it matters:** Every invocation of this endpoint (the "Generate New Credentials" flow for rotating Custom-Store creds) throws a Postgres "function does not exist" error and returns a 500. It has been broken since migration 008 shipped.
- **Fix:** Update the route to call the deterministic functions (matching `route.ts` GET/POST), or remove the endpoint if deterministic credentials make rotation-by-regeneration meaningless (regenerating gives the *same* password unless the API key changes, since it's derived, not random).
- **Effort:** S

### P0-4: Background/scheduled sync is dead end-to-end
- **Evidence, part A (wrong table):** `src/lib/services/backgroundSyncService.ts:197-216` (`getActiveStores`) queries `FROM stores s JOIN integrations i ON s.id = i.store_id WHERE i.integration_type = 'shipstation' AND i.is_active = true AND i.settings IS NOT NULL AND i.settings != '{}'`. The live schema has no `integrations` table and no `settings` column anywhere related to ShipStation — the real table is `store_integrations` with a `configuration` column (confirmed via `psql \dt`, and via every other sync route, e.g. `src/app/api/admin/sync/warehouses/route.ts:21-29`). The query throws, is caught at `backgroundSyncService.ts:212-215`, and silently returns `[]`. Every run logs "No active ShipStation integrations found" (line 46) and does nothing, forever.
- **Evidence, part B (even if fixed, auth fails):** `runSyncOperation` (`backgroundSyncService.ts:148-192`) calls the per-operation routes with `Authorization: Bearer <SYNC_AUTH_TOKEN>` (line 158). Those routes (e.g. `warehouses/route.ts:17`) authenticate via `requireAuth()`, which (`src/lib/auth/session.ts:100-113`) treats any Bearer token as a signed app JWT and calls `jwtVerify` on it. `SYNC_AUTH_TOKEN` is an arbitrary operator-configured string, not a JWT signed with `JWT_SECRET` — verification throws, falls through to cookie lookup (none present on a server-to-server call), and `requireAuth` throws `'Authentication required'`. So the two layers of this pipeline fail independently; fixing only one still leaves it broken.
- **Live confirmation:** `SELECT count(*) FROM sync_logs` returns `0`. The table that exists specifically to record background sync runs (migration `015_sync_logs_table.sql`) has never once been written to.
- **Why it matters:** This is the automation `CLAUDE.md` documents as the product's Heroku Scheduler story ("Configure Heroku Scheduler to run `npm run sync:background`"). It has never worked. Any merchant relying on nightly/hourly auto-sync to keep their storefront's stock and catalog current is silently getting nothing, with no error surfaced to them (the merchant-facing `/api/admin/sync/status` GET reports whatever's in `sync_logs`, i.e. nothing — not an error, just an empty history, which reads as "never run" rather than "broken").
- **Fix:** Point `getActiveStores` at `store_integrations`/`configuration`. Change the internal sync calls to use a dedicated service-to-service auth check (verify `SYNC_AUTH_TOKEN` directly, don't route it through `requireAuth`'s JWT verification) or call the sync functions in-process instead of over HTTP.
- **Effort:** M

### P0-5: Product catalog sync calls an endpoint that does not exist in the ShipStation API contract we have
- **Evidence:** `src/app/api/admin/sync/products/sync.ts:59` fetches `https://api.shipstation.com/v2/products?page=...`. `docs/shipstation-api-openapi.yaml` has no `/v2/products` path at all (the only match for "products" in the whole spec is a customs-declaration sub-schema field inside package/label bodies, `openapi.yaml:4566`, unrelated to a product catalog). The V2 API's actual product-adjacent surface, per this spec, is SKU-level inventory (`/v2/inventory`, `/v2/inventory_warehouses`, `/v2/inventory_locations`) — there is no documented resource carrying `name`, `description`, `thumbnail_url`, or `product_category` the way this code assumes (`products/sync.ts:42-52`, `132`, `154`).
- **Why it matters:** This is the sync operation that populates the merchant's storefront catalog — names, descriptions, images, categories — the single most load-bearing call in "my products are in my store." Per the contract this audit was told to check against, it is calling a URL with no documented `GET` operation. Either the endpoint doesn't exist in production (every sync run 404s and the whole catalog population silently fails past the `!productsResponse.ok` throw at line 66-69) or it exists but is entirely unspecified by the contract we have, so its request/response shape (pagination envelope, field names) cannot be verified as correct — the code's assumed shape (`{products: [...]}` with `product_id`, `customs_value.amount`, `thumbnail_url`, `product_category.name`) is unverifiable against anything in this repo.
- **Fix:** Get ShipStation to confirm the real product-catalog endpoint (if one exists for V2) or restructure product sync around the documented `/v2/inventory*` resources plus another source of truth for descriptive fields (ShipStation V2 doesn't model a rich product catalog — this may require accepting that catalog content has to come from somewhere other than ShipStation, which is a product-strategy question, not just a bug).
- **Effort:** L (may require product-level rethink, not just a code fix)

### P0-6: Order push (`POST /v2/shipments`) is not a documented operation in the OpenAPI contract
- **Evidence:** `src/lib/shipstation/v2Api.ts:395-402` (`createShipment`) does `fetch('https://api.shipstation.com/v2/shipments', { method: 'POST', ... })`. In `docs/shipstation-api-openapi.yaml`, the `/v2/shipments` path block (lines 1865-1922) defines only a `get:` (`operationId: list_shipments`) — there is no `post:` under this path anywhere in the file. A schema titled `create_shipment_response_body_fields` exists at line 3660 but is not referenced by any path's `requestBody`/`responses` — it's an orphaned schema, not a wired operation.
- **Why it matters:** This is the *only* mechanism in the codebase that gets a paid order into ShipStation (see "The order-push gap" below — it's not actually a gap, but it's unverifiable against the contract this audit was told to use as ground truth). We cannot confirm the request shape (`shipments[]` with `external_shipment_id`, `ship_to`, `ship_from`, `items`, `create_sales_order`) or response shape against anything the spec documents. If the spec in this repo is simply incomplete (real ShipStation V2 does have `POST /v2/shipments` in production), that's a documentation gap that should be fixed so this integration can be reviewed properly. If it's accurate and the operation genuinely isn't exposed this way, order push is calling a nonexistent endpoint and every checkout with ShipStation configured is failing at `v2Api.ts:411-417`, which is directly visible as `SHIPMENT_CREATION_FAILED` (`src/app/api/orders/route.ts:98-110`) — i.e. the sale fails.
- **Fix:** Reconcile `docs/shipstation-api-openapi.yaml` with the real, current ShipStation V2 contract (or obtain the authoritative one from ShipStation) before trusting this path further. This is a prerequisite to trusting any other correctness claim in this audit about the order-push flow.
- **Effort:** S (to flag/escalate) / L (to fully re-verify once a correct spec exists)

### P0-7: Webhook has no signature verification and no tenant scoping
- **Evidence:** `src/app/api/shipstation/webhook/route.ts:25` reads `x-shipstation-signature` but never validates it. `verifyWebhookSignature` (`src/lib/shipstation/auth.ts:361-364`) is fully implemented but has zero call sites anywhere in `src/` (confirmed by search). Downstream, `orderStatusService.findOrderByShipStationId` (`src/lib/services/orderStatusService.ts:371-398`) resolves the target order with `SELECT * FROM orders WHERE shipstation_order_id = $1` or `WHERE order_number = $1` — **no `store_id` predicate at all**.
- **Why it matters:** Anyone who can reach `/api/shipstation/webhook` (no auth of any kind is required) can POST a crafted `ITEM_SHIP_NOTIFY`/`ITEM_DELIVERED_NOTIFY` payload with any `order_id`/`resource_id` and mark *any store's* order as shipped/delivered with attacker-chosen tracking number, carrier, and label URL, and trigger a customer-facing notification job for it (`orderStatusService.ts:138-144`). This is a genuine cross-tenant integrity hole, not just a hardening gap.
- **Fix:** Verify `x-shipstation-signature` against a per-store secret before processing anything. Scope every order lookup by `store_id`, which means the webhook payload or URL needs to carry the store identity (ShipStation webhooks don't include your internal store_id by default — this likely requires a per-store webhook URL/token, e.g. `/api/shipstation/webhook/[storeToken]`).
- **Effort:** M

### P0-8: The webhook is never actually registered with ShipStation — likely unreachable in practice
- **Evidence:** ShipStation's documented webhook registration operation is `POST /v2/environment/webhooks` (`operationId: create_webhook`, `openapi.yaml:2245`). No code path anywhere in `src/` calls this endpoint (confirmed by search for `environment/webhooks`, `create_webhook`, `registerWebhook`). The only setup screen that mentions any of this is the legacy Custom-Store instructions (`admin/integrations/shipstation/page.tsx:659-681`), which is about the XML polling connection, not V2 webhooks.
- **Why it matters:** Directly answers audit question 5's second half: the webhook handler is well-built dead code. Nothing in the product ever tells ShipStation to send events here, so in the ordinary course of using the app, this route receives nothing. (It's also the reason P0-7 has had zero real-world blast radius so far — but that's luck, not safety, since the route is reachable by anyone who guesses the URL.)
- **Fix:** Call `create_webhook` during integration setup (subscribing to at least `SHIP_NOTIFY`/`ITEM_SHIP_NOTIFY` equivalents for the merchant's store), store the returned `webhook_id`, and surface subscription status in the admin UI.
- **Effort:** M

### P0-9: Credential "encryption" is base64; the "password hash" is base64 of the plaintext
- **Evidence:** `decryptApiKey`/`decryptApiSecret` (`src/lib/shipstation/auth.ts:12-18`) are `Buffer.from(x, 'base64').toString('utf-8')` — i.e., encoding, not encryption. The corresponding "encrypt" side (`src/app/api/admin/integrations/shipstation/route.ts:242-243`) is `Buffer.from(apiKey).toString('base64')`. The stored `shipstation_password_hash` is likewise `Buffer.from(generatedPassword).toString('base64')` (`route.ts:239`, and `generate-credentials/route.ts:59`) — base64 is reversible in one line, so this is not a hash in any meaningful sense.
- **Why it matters:** Anyone with read access to `store_integrations` (a DB credential leak, a misconfigured backup, an internal tool with over-broad access) recovers every merchant's live ShipStation API key and Custom-Store password in plaintext, trivially. Combined with P0-10 below, this also makes the deterministic Basic-Auth scheme fully computable offline once an attacker has the (trivially-decoded) API key.
- **Fix:** Use real authenticated encryption (e.g. AES-GCM with a KMS-managed key) for `api_key_encrypted`/`api_secret_encrypted`, and a real password hash (bcrypt/argon2) for `shipstation_password_hash`.
- **Effort:** M

### P0-10: Deterministic auth credentials are computable from data that isn't actually secret enough
- **Evidence:** `database/migrations/008_deterministic_shipstation_auth.sql:29-41` derives the Custom-Store Basic-Auth password as `md5(store_id || api_key || 'shipstation_salt_2025')` (truncated) `|| md5(api_key)` (truncated) — MD5, with a salt hardcoded in a migration file that lives in source control (visible to anyone with repo access, present or past), combined with the store's own API key (which per P0-9 is one `Buffer.from(..., 'base64')` away from plaintext if the DB is ever exposed).
- **Why it matters:** This turns a single leak (the base64 "encrypted" API key, or the salt+algorithm which is public in this repo) into full reconstruction of the Custom-Store credentials for the order-export XML endpoint, without needing direct access to `shipstation_username`/`shipstation_password_hash` at all.
- **Fix:** Once real encryption is in place (P0-9), also stop deriving auth credentials from data that isn't a proper secret — use a cryptographically random per-store secret for Custom-Store Basic Auth, stored (encrypted) rather than recomputed from other secrets.
- **Effort:** M (bundle with P0-9)

## P1 Findings

### P1-1: No rate-limit handling anywhere; inconsistent handling of a failed page mid-sync
- **Evidence:** Every sync loop (`products/sync.ts:58-77`, `91-107`; `inventory/sync.ts:28-47`) pages sequentially with zero delay and no inspection of `429` / any rate-limit header. On a `429`, the primary product-fetch loop throws and aborts the whole sync (`products/sync.ts:66-69`), while the *embedded* inventory fetch inside the same function silently treats any non-OK response as "no more pages" and moves on (`products/sync.ts:104-106`) — so a rate-limited inventory page is swallowed with no error and the resulting stock numbers are silently incomplete/wrong, while a rate-limited product page kills the run entirely. Two different failure behaviors for the same class of error, both wrong.
- **Why it matters:** ShipStation does rate-limit; a store with a large catalog synced on a schedule will eventually hit it, and the outcome today is either a hard failure or silently wrong stock counts — never a clean "back off and retry."
- **Fix:** Centralize a fetch helper that reads `X-Rate-Limit-Remaining`/`Retry-After` (or backs off exponentially on 429 generally), retries with backoff, and treats a failed page consistently (fail loud, always) rather than differently per call site.
- **Effort:** M

### P1-2: No pagination/time budget for large catalogs; N+1 queries; no `maxDuration`, no checkpoint
- **Evidence:** `syncProducts` (`products/sync.ts:120-190`) does, per product: an existence `SELECT` (line 123-126), a category lookup-or-create that's its own multi-query round trip (`getOrCreateCategory`, lines 12-32, called at line 133 for *every* product with no caching across the loop), then an `UPDATE`/`INSERT`. That's 3-5 sequential DB round trips per product with no batching and no transaction. No route under `src/app/api/admin/sync/**` declares `export const maxDuration`, so these run under Vercel's platform default. For a 5,000-product ShipStation account, this is on the order of 15,000-20,000 sequential DB queries plus ~100 sequential ShipStation page fetches (50 pages of products, 50 of inventory), run inside one HTTP request.
- **Why it matters:** Directly answers "what happens with 5,000 products" — the request almost certainly exceeds the serverless function's execution limit before finishing. There is no cursor/checkpoint recording how far the run got, so the merchant sees a timeout/500 with no indication of what synced and what didn't, and re-running restarts from page 1.
- **Fix:** Cache category lookups for the duration of a run (single map, resolved once). Batch upserts. Add `export const maxDuration` appropriate to the platform tier as a stopgap, but the real fix is the chunked/queued architecture described below.
- **Effort:** L

### P1-3: No transaction boundaries around sync writes
- **Evidence:** None of `products/sync.ts`, `inventory/sync.ts`, `warehouses/sync.ts`, `inventory-warehouses/sync.ts`, `inventory-locations/sync.ts` wrap their per-row writes in a transaction; each `UPDATE`/`INSERT` commits independently.
- **Why it matters:** A crash or timeout mid-run leaves a partially-updated catalog with no way to know, from the data alone, which rows are from this run and which are stale. Per-row upserts by external ID make individual retries mostly idempotent, but there's no run-level consistency (e.g., a product updated at minute 1 and inventory that failed to sync at minute 3 can disagree).
- **Fix:** Not necessarily one giant transaction (that would make the timeout problem worse) — but each run should be trackable (a `sync_run_id`) so partial progress is visible and resumable, per the target architecture below.
- **Effort:** M

### P1-4: `/api/admin/sync/status` leaks cross-tenant data and has an unchecked `storeId` IDOR
- **Evidence:** GET (`status/route.ts:11-62`) returns `sync_logs` history/statistics/recent errors to any authenticated user with a `storeId` — and it can't be scoped per-store because `sync_logs` (migration `015_sync_logs_table.sql`) has no `store_id` column at all. POST (`status/route.ts:172-210`) accepts a `storeId` from the request body and calls `syncService.syncStore({id: storeId})` (line 194) with no check that the authenticated user owns that store.
- **Why it matters:** Any merchant admin can see the platform-wide sync history/error messages of every other store, and (in the IDOR case) attempt to trigger a sync for a store they don't own — currently a no-op only because the downstream call independently fails auth (P0-4b); that should not be relied upon.
- **Fix:** Add a `store_id` column to `sync_logs`/`sync_history` and scope all reads by it; verify `storeId` in the POST body matches `user.storeId` (or that the user has admin rights over it) before calling `syncStore`.
- **Effort:** M

### P1-5: `job_queue` is written to but never drained
- **Evidence:** `jobQueueService.addJob` is called from the webhook handlers (`webhook/route.ts:183-191, 208-217, 238-248`) and from `orderStatusService.queueCustomerNotification` (`orderStatusService.ts:463-491`) to queue shipment/delivery emails. `jobQueueService.processJobs()`/`startProcessing()` (`jobQueueService.ts:85-127, 362-393`) are fully implemented with priority ordering and exponential-backoff retry — but there is no call site anywhere in the codebase for either (confirmed by search), no `vercel.json` cron config, and no `/api/**/cron`-style route that would invoke it.
- **Why it matters:** Every customer shipment/delivery notification this system claims to queue is written to a table and never read again. This looks like a working async system (it has retry logic, priority, backoff — real engineering effort went into it) and is actually a silent black hole. This is worse than not having the feature, because logs say "Queued shipped notification for order X" (`orderStatusService.ts:490`) which reads as success.
- **Fix:** Add a scheduled invocation (Vercel Cron hitting a small `/api/jobs/process` route, or fold into the background sync fix) that calls `jobQueueService.processJobs()` regularly.
- **Effort:** S once P0-4's scheduling story is fixed (ride the same cron)

### P1-6: Legacy XML order export reports totals 100x too small
- **Evidence:** `formatMoney` (`src/lib/shipstation/utils.ts:200-202`) computes `(amount / 100).toFixed(2)`, assuming amounts are stored in cents. Live data says otherwise: `SELECT sku, base_price FROM products` returns values like `29.99`, `2999.99` (decimal dollars); `SELECT order_number, total_amount FROM orders` returns `873.98`, `1403.99`. `xmlBuilder.ts:57-59` calls `formatMoney(order.total_amount)` when building the `<OrderTotal>`/`<TaxAmount>`/`<ShippingAmount>` fields for the `/api/shipstation/orders` GET export.
- **Why it matters:** Any consumer of the legacy XML order-export feed (the Custom-Store polling path) sees order totals two orders of magnitude too small — an $873.98 order exports as `8.74`. Note this bug does *not* affect the V2 shipment-push path (`v2Api.ts` passes `orderData.total` straight through in dollars, which is correct for V2's decimal money convention) — it's specific to the legacy XML feed.
- **Fix:** Remove the `/100` in `formatMoney`, or make the unit convention explicit and consistent store-wide.
- **Effort:** S

### P1-7: Debug logging leaks live API key fragments repeatedly
- **Evidence:** `v2Api.ts:229-234` and `:325-337` and `:384-393` log `api_key_length`, `first_6_chars`, `last_4_chars` of the real decrypted ShipStation API key on essentially every V2 API call. Same pattern in `warehouses/route.ts:41-45` and `sync/all/route.ts:70-75`.
- **Why it matters:** Given the key is only base64 "encrypted" at rest (P0-9), and 6+4=10 characters of a typical 32-40 char key is a meaningful fraction, this repeatedly writes sensitive material to logs (which are often more broadly accessible — CI logs, log aggregators, support tooling — than the database itself).
- **Fix:** Remove these debug logs, or gate them behind a build-time flag that's off in production.
- **Effort:** S

### P1-8: Legacy Basic-Auth lookup does an unscoped full-table decrypt-and-compare
- **Evidence:** `authenticateShipStationRequest` and `authenticateShipStationAPIKey` (`auth.ts:71-141`, `162-228`) both run `SELECT ... FROM store_integrations WHERE integration_type = 'shipstation' AND is_active = true` with **no store filter**, then loop over every row, decrypting and comparing credentials until one matches.
- **Why it matters:** Not a tenant-isolation bug by itself (the loop only succeeds on an exact match, so it doesn't leak store B's data to store A) but it's O(active ShipStation integrations) work — and combined with the weak "encryption," widens the blast radius of any timing/DB-load side channel as the merchant base grows. At 3 rows today it's invisible; it won't stay that way.
- **Fix:** Look up by `shipstation_username` directly (`WHERE shipstation_username = $1`) instead of scanning and decrypting every row.
- **Effort:** S

### P1-9: Inconsistent schema naming after the 014 rename
- **Evidence:** Migration `014_rename_warehouses_to_shipfroms.sql` renames `shipstation_warehouses` → `shipfroms` and adds `is_default` (lines 8-11), but `shipstation_inventory_warehouses` and `shipstation_inventory_locations` (created in migration `012_shipstation_warehouses.sql`) were left untouched. Confirmed live: `psql \dt` shows `shipfroms`, `shipstation_inventory_locations`, `shipstation_inventory_warehouses` side by side.
- **Why it matters:** Three ShipStation-address/location concepts now use three different naming conventions (`shipfroms` vs. `shipstation_inventory_warehouses` vs. `shipstation_inventory_locations`), which is exactly the kind of inconsistency that makes future migrations and onboarding new engineers slower and error-prone. It's cosmetic today but it's evidence the 014 rename was done for one table without a plan for the related ones.
- **Fix:** Either fully commit to the `shipfroms` naming rationale across all ShipStation-location tables in a follow-up migration, or document why `shipstation_inventory_*` intentionally stayed as-is (they map to a different ShipStation concept — "inventory warehouses/locations" for stock, vs. "warehouses" as ship-from addresses — which is a legitimate distinction, but nothing in the code or schema currently explains it).
- **Effort:** S (doc) / M (migration)

### P1-10: Two redundant, conflicting ShipStation setup UIs
- **Evidence:** `/admin/integrations/shipstation` (`shipstation/page.tsx`) is a dedicated 700-line screen for the legacy Custom-Store XML integration (username/password/apiKey/apiSecret/endpointUrl, fake test, broken credential display — see P0-1/P0-2). `/admin/integrations` (`page.tsx` + `IntegrationSettings.tsx`) is a generic multi-provider screen (ShipStation/Stripe/Square/PayPal) with a single API-key field, a *real* connectivity test (`/api/admin/integrations/test`), and it's what feeds `syncWarehouses`/`syncProducts`/etc. and the V2 order-push path that actually works.
- **Why it matters:** A merchant landing on the wrong screen (there's no indication either is deprecated, and the dedicated `/shipstation` URL reads as more authoritative) will configure the legacy integration — which per P0-1 through P0-3 is largely non-functional — while believing they've connected ShipStation. Both screens claim to be "the" ShipStation setup.
- **Fix:** Pick one. Given the V2 path is the one that's actually wired to sync and order push, retire the legacy Custom-Store screen (or clearly relabel it as an advanced/alternate mode) and make `/admin/integrations` the single entry point.
- **Effort:** M

## P2 Findings

- **No idempotency on webhook processing.** Nothing dedups on `resource_id`/`shipment_id` before applying an update (`webhook/route.ts`, `orderStatusService.ts:100-145`), so a ShipStation retry (or, per P0-7, a malicious replay) reprocesses and re-queues a customer notification each time. **Effort: S**, once P0-7/P0-8 are fixed and this route sees real traffic.
- **Synchronous, unretried order push blocks checkout.** `src/app/api/orders/route.ts:62-110` runs a credentials test *and* a shipment creation, each a single unretried `fetch` (`v2Api.ts:395-417`, `459-476`), inline in the checkout request. Any transient ShipStation error (not just a real outage — a slow response, a momentary 5xx) fails the sale outright with `SHIPMENT_CREATION_FAILED`. **Effort: M** — belongs in the target architecture below (decouple order push from the checkout critical path with a queued retry).
- **`skip type checking during build`** is set in `next.config.ts` (visible near the end of the config) — not ShipStation-specific, but worth flagging since it means TypeScript errors in any of the files above (several use loosely-typed `Record<string, unknown>` for API responses) won't block a deploy. **Effort: S** to at least scope-in the ShipStation directories.
- **`sync_history` table exists in the schema but has no code reference anywhere in `src/`** — either genuinely vestigial or a planned table that was never wired up; worth a decision either way rather than leaving it ambiguous. **Effort: S** (decide + document, or drop).
- **`integration_alerts` is written to (`monitoringService.ts:489`) but never read by any admin UI** (`grep` for the table under `src/app` returns nothing) — alerts are generated and then invisible to the merchant. **Effort: S** to add a simple admin panel, or stop writing them if there's no plan to surface them.

## The order-push gap

Order push is **not** missing — this is worth stating clearly since it's the most consequential possible finding and the codebase does contain a real attempt at it. When a store has V2 credentials configured, `POST /api/orders` (`src/app/api/orders/route.ts:47-131`) does:

1. Look up V2 credentials for the store (`getShipStationV2Credentials`, `v2Api.ts:207-249`).
2. Test them live against ShipStation (`testShipStationV2Credentials`, `v2Api.ts:459-484`) and hard-fail the order if invalid.
3. Build a shipment payload (`transformToV2Shipment`, `v2Api.ts:283-366`) with `ship_to`, `ship_from` (pulled from the `shipfroms` table or a hardcoded placeholder fallback, lines 309-321), line items with real SKUs looked up from `products` (lines 288-300), and `create_sales_order: true`.
4. POST it to `https://api.shipstation.com/v2/shipments` (`createShipment`, `v2Api.ts:371-454`).
5. Only write the local `orders` row after ShipStation accepts it (`createCompletedOrder`, `orders/route.ts:90-96`), tagging it `shipstation_order_id` and `payment_method: 'shipstation_v2'`.

What's genuinely wrong with it, beyond what's already listed above as P0-6:

- **No payment gateway anywhere in this path.** `payment_status` is set to `'completed'` unconditionally (`orders/route.ts:253`) with no Stripe/Square/PayPal charge call visible in this file or its imports. Whatever collects money must happen entirely client-side or upstream of this route; as written, hitting this endpoint directly creates a real ShipStation shipment and a local "completed, paid" order with nothing enforcing that payment occurred. That's outside this audit's ShipStation scope strictly speaking, but it's load-bearing context for how much trust to put in "order push works."
- **No retry/backoff, and it runs inline in the checkout request** (P2, above) — a transient failure loses the sale rather than queuing for retry.
- **`create_sales_order: true` conflates "create a shipment" with "create an order."** Using the shipment-creation call to *also* create the underlying ShipStation order/sales-order record (rather than a dedicated order-creation call) means a merchant can't get an order into ShipStation without simultaneously kicking off shipment creation — there's no way to push "here's a paid order to fulfill" and let the merchant decide packaging/rates/label timing in ShipStation itself, which is normally how fulfillment teams work. This may be a reasonable choice if V2 genuinely has no separate order-creation endpoint (per this audit's OpenAPI spec, there is no `/v2/orders` path at all), but it's worth being explicit that "order push" here really means "immediately create a shipment," not "hand off an order for the merchant to process."

If ShipStation's real V2 contract does have a documented `POST /v2/shipments` (P0-6's uncertainty), what exists is a reasonable first version of order push, missing retry/queueing and payment-gateway integration. If it doesn't, this is calling a nonexistent endpoint and order push does not actually work in production — this needs to be resolved with ShipStation directly before anything else in this section can be trusted.

## Recommended target architecture

**Stop running sync inline in HTTP request handlers.** Every sync operation today is "receive HTTP request → loop through ShipStation pages → loop through DB writes → return HTTP response," all inside one Vercel function invocation with no `maxDuration` override and no checkpointing. That model cannot survive a real catalog size (P1-2) and has already produced one dead pipeline (P0-4) because the "background" story was bolted on as another HTTP call rather than a real job.

**The repo already has a `job_queue` table with solid queue semantics (priority, retry count, backoff, status transitions) — it is not vestigial in design, only in operation (P1-5: nothing drains it).** The right fix reuses this table rather than introducing a second queueing mechanism:

1. **Chunk sync into jobs, not one request.** A "sync products" run should enqueue one `job_queue` row per page (or per N products) instead of looping 50 pages in one request. Each job fetches one page from ShipStation, upserts it, and (if there's a next page) enqueues the next page's job. This naturally fits inside any serverless timeout because each unit of work is small and bounded, and a crash mid-run loses at most one page, not the whole catalog.
2. **Drive the queue with Vercel Cron, not `setInterval`.** `jobQueueService.processJobs()` already exists and is correct; it just needs a `vercel.json` cron entry (e.g. every 1-5 minutes) hitting a thin `/api/jobs/process` route that calls it, processing a bounded batch (`BATCH_SIZE = 10`, already defined) per invocation. This single mechanism also fixes P1-5 (customer notifications) for free, since it's the same drain loop.
3. **Track sync runs with a cursor, not just a count.** Add a `sync_runs` (or repurpose the existing, currently-unused `sync_history` table) row per triggered sync with `store_id`, `operation`, `status`, `last_page_completed`, `started_at`, `finished_at`. Resuming after a partial failure means "find the last incomplete run, continue from `last_page_completed`," not "start over from page 1." This also directly fixes the multi-tenant leak in P1-4 by giving `sync_logs`/history a `store_id` to filter on.
4. **Keep webhook-driven updates for anything ShipStation can push, and only poll for the rest.** Once P0-7/P0-8 are fixed (real signature verification, real subscription via `create_webhook`, per-store scoping), shipment/tracking updates should arrive via webhook, not be re-derived by polling. Scheduled sync should be reserved for catalog/inventory, where ShipStation is the source of truth and there's no webhook equivalent for "a product changed."
5. **Keep order push out of the checkout critical path.** On order creation, write the local order row first (payment already confirmed by whatever gateway is actually charging the customer — see the order-push section above), then enqueue a `job_queue` job to create the ShipStation shipment with real retry/backoff. Surface `fulfillment_sync_status` on the order (`pending`/`pushed`/`failed`) in the merchant's order list so a failed push is visible and retriable, instead of failing the sale outright.
6. **Rate-limit and back off at the fetch layer, once, centrally.** A single `shipStationFetch(url, opts)` helper that retries on 429/5xx with exponential backoff and respects `Retry-After` should replace the dozen hand-rolled `fetch` calls scattered across `v2Api.ts` and the five `sync/*.ts` files, so the "sometimes we throw, sometimes we silently truncate" inconsistency (P1-1) becomes structurally impossible.

This is a moderate rewrite, not a rebuild — the pieces (job queue, per-store credentials, upsert-by-external-id sync logic) are mostly right; they're just wired together as synchronous request/response instead of as an actual pipeline.

## What is actually good

- **The `job_queue` table and `jobQueueService` implementation are well-designed** — priority ordering, exponential backoff (`RETRY_DELAYS = [1000, 5000, 15000]`), max-attempt handling, a `getFailedJobs`/`retryJob` operator escape hatch (`jobQueueService.ts:492-541`). The only problem is nothing calls it (P1-5); the design itself is sound and is exactly the primitive the target architecture above builds on.
- **Sync logic upserts by ShipStation's own external ID** (`shipstation_product_id`, `warehouse_id`, `inventory_warehouse_id`, `inventory_location_id`) rather than by name or position, which makes individual row-level retries safe and re-runs idempotent at the row level even though runs aren't tracked end-to-end (P1-3).
- **The generic integration test at `/api/admin/integrations/test`** does a real live check against ShipStation (`GET /v2/warehouses`) and even handles the "401 because billing/plan, not because the key is wrong" case thoughtfully (`test/route.ts:111-133`) — genuinely good error-message engineering, better than most integrations bother with. It's just wired to the wrong screen (P1-10).
- **Order creation is wrapped in an explicit `BEGIN`/`COMMIT`/`ROLLBACK` transaction** (`orders/route.ts:230-441`) covering the order row, order items, inventory deduction, and coupon usage together — this is the one place in the ShipStation-adjacent code that gets transactional integrity right.
- **The V2 credential/auth header usage matches the documented contract.** `docs/shipstation-api-openapi.yaml:2547-2554` specifies `api-key` as a header-based API key, and every V2 call in `v2Api.ts` and the `sync/*.ts` files uses exactly that (`headers: { 'api-key': apiKey }`) — this part of the integration is correct against the spec even where other parts (P0-5, P0-6) aren't.
- **Money handling on the V2 path is correct.** Unlike the legacy XML path (P1-6), `transformToV2Shipment` passes `orderData.total` straight through as decimal dollars, matching V2's `monetary_value`-style convention and the live DB's actual storage format — no unit-conversion bug there.
