# Demo data

The three demo/marketing stores are seeded by a single script, `scripts/seed-demo.js`, using
hand-drawn SVG art generated by `public/demo/generate-art.js` + `public/demo/catalog.js`. This
document is the map: what exists, where the IDs are, how to regenerate art, and how to reseed.

## The three stores

| Store | Slug (unchanged) | UUID (unchanged) | Theme | Products | Accent |
|---|---|---|---|---|---|
| **Basecamp Audio** | `demo-electronics` | `650e8400-e29b-41d4-a716-446655440001` | `dark` | 12 | Graphite ink body, ember (`#F94E1B`) signal LED |
| **Fernwood Goods** | `artisan-craft` | `650e8400-e29b-41d4-a716-446655440002` | `amber` | 12 | Clay / linen / wood tones, ember wax-seal dot |
| **Ironline Fitness** | `fitness-pro` | `650e8400-e29b-41d4-a716-446655440003` | `teal` | 12 | Charcoal rubber + steel, mint (`#0FA871`) signal dot |

Store UUIDs and slugs are exactly what shipped in the original thin seed — nothing else in the app
had to change to pick these up. Store *names*, copy, theme and catalog are new.

Each store has: 4 categories, 12 products (one out of stock, two low-stock, the rest healthy), 2
coupons, 3 published blog posts, 20–28 orders with line items spread over the last 90 days
(mixed `completed` / `shipped` / `processing` / `pending` / `cancelled`), ~90 days of `visitors`
rows and ~60–110 `search_tracking` rows, and 30 days of `store_analytics_summary`. Owner users and
their IDs are unchanged from the original seed (`demo@schmostore.com`, `store.owner@example.com`,
`another.user@example.com`), sharing the same pre-existing dev bcrypt fixture hash the original
seed used — this script doesn't know or assert what the underlying plaintext password is.

Product SKUs use a per-store prefix so they sort together: `BCA-*` (Basecamp Audio), `FWG-*`
(Fernwood Goods), `IFT-*` (Ironline Fitness). Full product list, prices, copy, weights and
dimensions live in the `STORES` array in `scripts/seed-demo.js` — that file is the single source
of truth for every piece of demo content (copy, prices, stock, coupons, blog posts, order
generation rules).

Each store also gets three `store_config` rows other agents can read:

- `hero_image_url` — path to the store's wide hero SVG (see below)
- `tagline` — short one-line brand tagline
- `shipping_free_threshold` / `shipping_flat_rate` — used to compute realistic order shipping

`stores.logo_url` and `stores.favicon_url` both point at the store's generated logo mark SVG.

## The art

Everything under `public/demo/` is generated, checked-in SVG — no rasters, no remote URLs, no
embedded fonts (only the candle label and a couple of jar labels use `font-family="sans-serif"`,
a generic family, per the design system's asset rules).

```
public/demo/
  generate-art.js   # SVG primitive library (gradients, cylinders, spheres, ground shadow, etc.)
  catalog.js         # per-store product/hero/logo art direction (the actual illustrations)
  build.js            # runs catalog.js through generate-art.js and writes the files below
  products/*.svg      # 36 square (800x800) product studio shots, one per SKU
  hero/*.svg           # 3 wide (1600x900) store hero banners
  logo/*.svg            # 3 small (160x160) brand marks
```

Composition rules baked into every product image (see `generate-art.js` header comment for the
exact numbers): a warm paper background wash tinted per store, a blurred ground-contact shadow at
a fixed baseline, a top-left key light on every gradient, one constant stroke weight, and exactly
one recurring "signal" accent dot per product (an LED, a wax seal, a stitched tab) in the store's
accent color — the thread that ties a 36-item catalog together visually.

**To regenerate the art** (e.g. after editing `catalog.js`):

```bash
node public/demo/build.js
```

This is idempotent and deterministic — no `Math.random()`, no network access, same input always
produces byte-identical SVGs. It overwrites everything in `public/demo/{products,hero,logo}/`.

To sanity-check a change visually before reseeding the DB, build a quick HTML contact sheet that
`<img src>`s the files in `public/demo/products/` and screenshot it — there is no automated visual
test for the art itself.

## Reseeding the database

```bash
node scripts/seed-demo.js            # wipe + reload the 3 demo stores, then regenerate the SQL snapshot below
node scripts/seed-demo.js --no-dump  # same, but skip regenerating database/seeds/development.sql
```

Requires `DATABASE_URL` (falls back to reading it out of `.env.local` if the env var isn't set).
The script is transactional (one `BEGIN`/`COMMIT` for the whole run) and **scoped** — every
`DELETE` filters on the three known store UUIDs (and their three owner user IDs), so it never
touches a store or user created by anyone/anything else, even in a shared database. It has been
run back-to-back twice with identical results (same product/order/category counts) to confirm
idempotency.

One subtlety: inserting `order_items` fires a DB trigger
(`trigger_update_inventory_on_order` → `update_product_stock`) that decrements
`products.stock_quantity` as a side effect, and also writes `inventory_logs` rows. The script
accounts for this on purpose — it plans the full 90-day order history in memory first, sums how
many units of each SKU that history "sells," and inserts each product with its stock pre-loaded by
that amount. After the order/order-item inserts run, stock lands exactly on the intended target
(0 for the one out-of-stock item per store, low for the two low-stock items, healthy for the
rest) — so the current stock numbers are a real consequence of the order history, not two
disconnected fixtures.

### `database/seeds/development.sql`

This file is a **generated artifact**, not hand-maintained. After `seed-demo.js` commits, it reads
every row it just wrote back out of the database and serializes it to plain `INSERT` statements
(handled by the `dumpDevelopmentSql()` / `sqlLiteral()` helpers at the bottom of the script), so it
is always in sync with whatever `scripts/seed-demo.js` actually produced — there is no separate
copy of the catalog data to keep up to date by hand. It's meant as a readable, `psql -f`-loadable
snapshot (useful for CI fixtures or a quick manual load without Node), and its own scoped
delete-then-insert statements were verified to load cleanly end to end via
`psql -f database/seeds/development.sql`. It intentionally omits `visitors` and `search_tracking`
(thousands of low-value rows) — re-run the Node script to get those back.

For day-to-day reseeding, prefer `node scripts/seed-demo.js` over loading the `.sql` file directly:
the Node path is the one that correctly pre-loads stock to account for the inventory-deduction
trigger described above.

## Verifying after a reseed

```sql
-- counts
select store_slug, count(*) from products p join stores s on s.id=p.store_id group by 1;
select count(*) from products where featured_image_url is null; -- should be 0
select store_slug, count(*) filter (where stock_quantity = 0) from products p join stores s on s.id=p.store_id group by 1; -- 1 per store
```

Then look at it: with the dev server already running on port 3000, screenshot
`/store/demo-electronics`, `/store/artisan-craft`, `/store/fitness-pro` (and a product detail page,
e.g. `/store/demo-electronics/product/BCA-AUD-1001` — the product route resolves by SKU or DB id,
not by slug) and confirm images load, prices/discounts render, and the one out-of-stock item per
store shows a disabled "Out of Stock" state.
